1. Po co to wszystko — trzy sposoby, w jakie zawodzi zdalne wywołanie

Lokalne wywołanie metody ma dwa wyniki: zwraca wartość albo rzuca wyjątek. Zdalne wywołanie ma trzeci stan — milczy. I nikt ci nie powie, jak długo będzie milczeć.

To rozróżnienie jest fundamentem całego wykładu. Zdalna zależność może zawieść na trzy jakościowo różne sposoby, a każdy wymaga innej odpowiedzi:

Tryb porażkiJak wyglądaWłaściwa odpowiedź
Twardy błąd5xx, connection refusedponów (może trafisz na zdrową replikę), a przy serii — odetnij
Degradacjaodpowiada, ale coraz wolniejwykryj po czasie, nie po kodzie błędu — inaczej jest niewidzialna
Ciszapołączenie żyje, odpowiedzi braktimeout — jedyna rzecz, która przerwie czekanie
Kontekst historyczny

Na początku lat 90. w Sun Microsystems spisano Fallacies of Distributed Computing — listę fałszywych założeń, które programiści przyjmują po cichu: „sieć jest niezawodna", „opóźnienie jest zerowe", „zasoby są nieskończone". Wzorce, o których mowa w tym wykładzie, to nie moda ani cecha jednej biblioteki — to odpowiedzi na konkretne pozycje z tej listy. Dlatego mają swoje odpowiedniki wszędzie: Polly w .NET, gobreaker w Go, Tenacity w Pythonie, outlier detection w Envoy.

Drugi fundament, mniej oczywisty: sam mechanizm obrony nic nie znaczy, jeśli nie widać, że zadziałał. Retry, który po cichu ratuje 30% wywołań, ukrywa przed tobą fakt, że zależność jest chora. Circuit breaker, który otworzył się w nocy i sam zamknął, nie istnieje, jeśli nikt tego nie zmierzył. Stąd druga połowa tego wykładu to metryki — nie jako dodatek, tylko jako część mechanizmu.

2. Nasz przypadek: jedno wywołanie HTTP między serwisami

W systemie rezerwacji doków kosmicznych klient trafia przez gateway do starport-registry (dwie repliki), który rezerwuje dok. Rezerwacja potrzebuje trasy, więc starport-registry pyta synchronicznie trade-route-planner (też dwie repliki, za Eureką).

klient → api-gateway → starport-registry ──HTTP POST /api/v1/routes/plan──→ trade-route-planner (2 repliki) ▲ (2 repliki) │ to wywołanie jest bohaterem całego wykładu

Cały kod, o którym mowa, żyje w jednej klasie: TradeRoutePlannerHttpAdapter — adapterze portu RoutePlanner w architekturze heksagonalnej. To ważne: odporność jest szczegółem adaptera, a nie domeny. Domena wie tylko, że trasy czasem nie da się uzyskać.

Dlaczego dwie repliki mają znaczenie? Bo uzasadniają retry. Load balancer wybiera instancję przy każdej próbie, więc jeśli jedna replika jest chora, druga próba ma realną szansę trafić na zdrową. Bez tego retry byłby tylko powtarzaniem tego samego pytania pod ten sam adres.

3. Fundament: timeout, czyli obrona przed ciszą

Zanim jakikolwiek wzorzec z biblioteki: timeout na kliencie HTTP. To jedyna rzecz, która chroni przed trzecim trybem porażki. Bez niego wątek czeka tyle, ile pozwoli system operacyjny — czyli w praktyce w nieskończoność.

downstream:
  http:
    connect-timeout-ms: 200    # nawiązanie połączenia — szybko albo wcale
    read-timeout-ms: 2000      # oczekiwanie na odpowiedź (w profilu demo: 800)

Timeout ustawiamy na RestClient przez request factory, nie adnotacją. Warto wiedzieć dlaczego:

Pułapka: @TimeLimiter nie zadziała na metodzie synchronicznej

Resilience4j ma wzorzec TimeLimiter, ale wymaga on metody zwracającej CompletionStage (albo typ reaktywny, jeśli masz odpowiednie rozszerzenie na classpathie). Nasza metoda zwraca Route. Adnotacja by się skompilowała — i przy pierwszym wywołaniu TimeLimiterAspect rzuciłby IllegalReturnTypeException: „…has unsupported by @TimeLimiter return type. CompletionStage expected." Czyli nie martwa adnotacja, tylko mina rozbrajana dopiero w runtime. Usunęliśmy też martwą sekcję timelimiter: z application.yml, żeby nie sugerowała ochrony, której nie ma. Timeout robi tu klient HTTP i tylko on.

„Synchroniczna" znaczy tu coś węższego, niż myślisz

Uwaga na subtelność, bo w tym projekcie jest ona wyjątkowo myląca: to wywołanie już wykonuje się asynchronicznie. Warstwę wyżej ReservationCalculationService uruchamia je przez CompletableFuture.supplyAsync(…, VIRTUAL_EXECUTOR) równolegle z naliczaniem opłaty. Kod leci na osobnym wątku wirtualnym.

A mimo to dla Resilience4j metoda jest synchroniczna — bo aspekt patrzy wyłącznie na typ zwracany adnotowanej metody, a nie na to, gdzie fizycznie biegnie kod. Route to zwykła wartość, więc nie ma czego owinąć w limit czasu. ⚓ Asynchroniczny w słowniku R4j znaczy „sygnatura zwraca CompletionStage", nie „wykonuje się poza wątkiem wywołującego".

Jak musiałaby wyglądać, żeby @TimeLimiter zadziałał

Dziś — synchroniczna sygnatura
public interface RoutePlanner {
    Route calculateRoute(ReserveBayCommand command);          // ← zwykła wartość
}

// a asynchroniczność siedzi u WOŁAJĄCEGO:
CompletableFuture<Route> routeFuture =
        CompletableFuture.supplyAsync(() -> routePlanner.calculateRoute(command), VIRTUAL_EXECUTOR);
Wersja, którą R4j uzna za asynchroniczną
public interface RoutePlanner {
    CompletableFuture<Route> calculateRoute(ReserveBayCommand command);   // ← CompletionStage
}

@Retry(name = "trade-route-planner")
@CircuitBreaker(name = "trade-route-planner", fallbackMethod = "circuitOpenFallback")
@TimeLimiter(name = "trade-route-planner")                     // ← teraz ma co owijać
public CompletableFuture<Route> calculateRoute(ReserveBayCommand command) {
    return CompletableFuture.supplyAsync(() -> callTradeRoutePlanner(command), VIRTUAL_EXECUTOR);
}

// fallback też musi zwracać CompletableFuture:
private CompletableFuture<Route> circuitOpenFallback(ReserveBayCommand cmd, CallNotPermittedException e) { … }

Wołający uprościłby się symetrycznie — ReservationCalculationService nie musiałby już sam robić supplyAsync dla trasy, tylko złączyłby zwrócony future.

…i cztery rzeczy, które ta zamiana przynosi w pakiecie
  1. Anulowanie nie przerywa blokującego I/O. To najważniejsze. TimeLimiter po upływie limitu woła future.cancel(true), ale CompletableFuture ignoruje flagę przerwania (javadoc: „interrupts are not used to control processing"). Wołający dostanie TimeoutException natychmiast, a wątek roboczy dalej wisi na gnieździe aż do read-timeoutu. Limit czasu byłby więc pozorny — chroniłby wołającego, nie zasób.
  2. Każdy wyjątek przychodzi opakowany w CompletionException. Wasz pomocnik join(), który to rozpakowuje (żeby 409/503 nie zamieniło się w 500), staje się jeszcze bardziej krytyczny — i musiałby objąć też TimeoutException.
  3. Cebula rośnie o kolejną warstwę. Domyślnie TimeLimiter siedzi wewnątrz breakera, więc timeout stałby się porażką liczoną przez bezpiecznik — trzeba by świadomie zdecydować, gdzie go umieścić w cebuli.
  4. Kontekst obserwowalności. Przeniesienie supplyAsync do adaptera wymaga, żeby to on propagował kontekst trace'u — dziś robi to ContextExecutorService w serwisie kalkulacji (ADR-0017). Bez tego Observation zaczęłaby nowy, oderwany trace.
Werdykt dla tego systemu

Nie warto. Read-timeout na kliencie HTTP robi to samo lepiej: faktycznie zrywa odczyt z gniazda i zwalnia wątek, nie wymaga dodatkowej puli ani opakowywania wyjątków, i nie dokłada warstwy do cebuli. TimeLimiter zarabia na siebie tam, gdzie wywołanie nie ma własnego mechanizmu limitu — np. długie zadanie obliczeniowe albo klient bez konfigurowalnego timeoutu.

Zapamiętaj tę drabinę progów — wrócimy do niej wielokrotnie:

0 ms ──────── 500 ms ──────── 800 ms ─────────────→ zdrowo │ "wolne" │ timeout = porażka │ │ slow-call-duration-threshold read-timeout (profil demo)

Progi są ustawione celowo w tej kolejności: wywołanie, które trwa 600 ms, kończy się sukcesem (jest pod timeoutem), ale zostaje zapisane jako „wolne". Dzięki temu system wykrywa degradację, zanim zamieni się ona w błędy. Gdyby próg „slow" był powyżej timeoutu, nigdy by się nie uruchomił — każde wolne wywołanie stałoby się wcześniej porażką.

4. Circuit breaker: trzy stany, okno i dwa progi

Metafora jest dosłowna: bezpiecznik w domu nie istnieje po to, żeby prąd nigdy nie znikał — istnieje po to, żeby dom się nie spalił. Iskrzy → odcina.

Trzy stany

StanCo robiKiedy przechodzi dalej
CLOSED
zamknięty		ruch płynie normalnie, ale bezpiecznik cały czas liczy wyniki w okniegdy failure rate lub slow-call rate przekroczy próg → OPEN
OPEN
odcięty		odrzuca wywołania natychmiast (CallNotPermittedException), nie dotykając zależnościpo wait-duration-in-open-state → HALF_OPEN
HALF_OPEN
półotwarty		przepuszcza permitted-number-of-calls prób na próbępróby OK → CLOSED; próby padają → z powrotem OPEN

Kluczowa intuicja, którą łatwo przeoczyć: stan OPEN chroni nie tylko nas. Zależność właśnie leży; ostatnie, czego potrzebuje, to tysiąc requestów na sekundę od klienta, który „przecież musi spróbować". Nie dobijamy leżącego — dajemy mu szansę wstać.

Dwa progi, nie jeden

Nasz breaker liczy dwie rzeczy równolegle, i to jest najważniejsza rzecz w całej konfiguracji:

  • failure-rate-threshold: 50 — procent wywołań zakończonych wyjątkiem
  • slow-call-rate-threshold: 50 przy slow-call-duration-threshold: 500ms — procent wywołań, które zakończyły się sukcesem, ale trwały ≥ 500 ms
Dlaczego to jest sedno

Awaria typu „niby działa" — zależność odpowiada poprawnie, tylko pięć razy wolniej — nigdy nie zostanie złapana przez licznik 5xx. Dashboard zielony, SLA zielone, deploy zielony, a klient czeka. Slow-call detection to jedyny mechanizm w tym zestawie, który to widzi. W naszym demo wstrzyknięcie 600 ms latencji otwiera obwód przy zerowym liczniku błędów — bo wszystkie wywołania kończą się sukcesem, tylko wolno.

Okno przesuwne — o czym mówi „50%"

sliding-window-type: COUNT_BASED
sliding-window-size: 10       # bierzemy pod uwagę 10 ostatnich wywołań
minimum-number-of-calls: 5    # poniżej 5 nie liczymy nic (metryka pokazuje -1)
wait-duration-in-open-state: 10s
permitted-number-of-calls-in-half-open-state: 3

Okno licznikowe (10 ostatnich wywołań) ma konsekwencję, którą trzeba znać: przy niskim ruchu pamięta wywołania sprzed godzin, a przy wysokim reaguje na ostatnie kilkaset milisekund. Dla zależności HTTP w produkcji zwykle lepsze jest okno czasowe (TIME_BASED, np. 60 s). Zostawiliśmy licznikowe świadomie — cała choreografia demo jest pod nie skalibrowana — i wpisaliśmy zamianę do backlogu.

Wartość -1 w metryce resilience4j_circuitbreaker_failure_rate nie oznacza błędu: znaczy „za mało wywołań, nie mam zdania". Na dashboardzie mapujemy ją na myślnik, żeby nikt nie interpretował jej jako zera.

5. Retry: kiedy naprawdę ma sens

Jedna zasada porządkuje wszystko: ponawiaj tylko to, co w ogóle mogło się udać.

Rodzaj porażkiCzy ponawiać?Dlaczego
5xx, timeout, connection refusedTAKprzejściowe — serwer się zakrztusił, instancja wstawała; druga próba trafi na inną replikę
4xx (zły payload, brak uprawnień, odmowa domenowa)NIEdeterministyczne — to twoje pytanie było złe; drugie zadane tak samo da tę samą odpowiedź

Ponawianie 4xx nie jest tylko marnowaniem czasu. Jest gorsze: każda taka próba ląduje w oknie breakera jako nieudane wywołanie. Karmisz bezpiecznik własnymi bugami — zamiast pilnować, czy zależność żyje, dławi się twoimi czterysta-czwórkami i odcina zdrowy serwis.

Kontrapułapka — nie przesadź w drugą stronę

Kusi, żeby machnąć ręką i wykluczyć całe RuntimeException „żeby było spokojnie". Wtedy robisz coś znacznie gorszego: oślepiasz bezpiecznik. Przestaje widzieć realne porażki i nigdy się nie otworzy — a to on jest twoją siatką bezpieczeństwa. Wykluczaj wąsko, po konkretnych typach, i uzasadnij każdy wpis komentarzem.

Dygresja: czym jest RuntimeException i dlaczego akurat on oślepia

RuntimeException to klasa bazowa wyjątków niekontrolowanych (unchecked) — takich, których kompilator nie każe ci ani deklarować w throws, ani łapać. Zobacz, gdzie w tej hierarchii siedzą nasze typy:

Throwable ├── Error ← awarie JVM (OutOfMemoryError, StackOverflowError) │ nie łapiemy — nie da się sensownie zareagować └── Exception ├── checked ← IOException, SQLException… │ kompilator WYMUSZA throws albo catch └── RuntimeException ← unchecked: kompilator nie wymaga niczego ├── NullPointerException, IllegalArgumentException, IllegalStateException ├── ResourceAccessException ← Spring: TIMEOUT trafia tutaj ├── CallNotPermittedException ← Resilience4j: obwód otwarty └── RouteUnavailableException ← NASZ typ bazowy ├── RoutePlanningRejectedException (4xx — odmowa domenowa) └── RoutePlannerUnavailableException (5xx / timeout — awaria)

Zwróć uwagę na dolne trzy poziomy: wszystkie nasze wyjątki są RuntimeException. A Resilience4j dopasowuje wpisy z ignore-exceptions przez isAssignableFrom, czyli razem z całym poddrzewem podklas. Wpisanie tam RuntimeException znaczy więc dosłownie: „ignoruj RoutePlannerUnavailableException, ignoruj timeouty, ignoruj 5xx, ignoruj wszystko".

W aplikacji Springowej praktycznie każdy wyjątek docierający do bezpiecznika jest niekontrolowany — bo Spring opakowuje kontrolowane wyjątki I/O w niekontrolowane (SocketTimeoutException → ResourceAccessException). Efekt: okno nigdy nie zapisuje ani jednej porażki, failure_rate stoi na zerze, obwód nie otworzy się nigdy. Bezpiecznik istnieje, jest skonfigurowany, ma metryki — i nie zadziała. To gorsze niż jego brak, bo brak widać w kodzie, a ten stan wygląda na zabezpieczenie.

Dlaczego w ogóle używamy wyjątków niekontrolowanych

  1. Rollback transakcji. Spring domyślnie wycofuje @Transactional tylko dla RuntimeException i Error. Kontrolowany wyjątek domenowy zostawiłby zatwierdzoną, częściową rezerwację.
  2. Lambdy. Kontrolowane wyjątki nie przechodzą przez interfejsy funkcyjne — nasze Observation.observe(() -> …) po prostu by się nie skompilowało.
  3. Czystość portu. RoutePlanner deklaruje Route calculateRoute(cmd), a nie listę pięciu wyjątków infrastrukturalnych, o których domena nie powinna wiedzieć.
Reguła do zapamiętania

Każdy wpis na liście wykluczeń to zdanie „ta awaria mnie nie interesuje". Im wyżej w hierarchii wpis, tym więcej awarii obejmuje — a RuntimeException obejmuje wszystkie. Bezpieczniejszy wariant niż czarna lista: record-exceptions z konkretnym typem awarii, czyli biała lista — wtedy domyślną odpowiedzią jest „nie liczę", a nie „liczę". Uwaga na priorytet: w Resilience4j ignore-exceptions wygrywa z record-exceptions.

6. Punkt wyjścia — kod przed zmianami i cztery ukryte problemy

Tak wyglądał adapter przed pracami na gałęzi demo. Kod nie był zły — miał timeout, breaker, retry, metryki i fallback. Był lepszy niż większość tego, co widuje się w produkcji. A mimo to zawierał cztery problemy, z których każdy ujawnia się dopiero w awarii.

Przed
@Retry(name = "trade-route-planner")
@CircuitBreaker(name = "trade-route-planner", fallbackMethod = "routeUnavailableFallback")
public Route calculateRoute(ReserveBayCommand command) { ... }

private Route routeUnavailableFallback(ReserveBayCommand command, Throwable t) {
    incrementErrorCounter("circuit_open");
    throw new RouteUnavailableException(from, to, t);
}

// w callTradeRoutePlanner():
.onStatus(HttpStatusCode::is4xxClientError, (req, res) -> {
    incrementErrorCounter("domain");
    throw new RouteUnavailableException(from, to);          // ← ten sam typ
})
.onStatus(HttpStatusCode::is5xxServerError, (req, res) -> {
    incrementErrorCounter("infrastructure");
    throw new RouteUnavailableException(from, to);          // ← ten sam typ
})
// ...
catch (Exception e) {                                        // timeout
    incrementErrorCounter("infrastructure");
    log.error("Failed to plan route...", e);
    throw new RouteUnavailableException(from, to, e);        // ← i znowu ten sam
}

A w konfiguracji: brak ignore-exceptions, brak record-exceptions, brak aspect-order, retry ponawiający RouteUnavailableException — czyli wszystko.

Cztery problemy

  1. Fallback łapie Throwable — czyli także twoje własne NullPointerException i nawet OutOfMemoryError. Każdy z nich zostaje zaetykietowany jako circuit_open.
  2. Jeden typ wyjątku na trzy różne awarie — breaker i retry nie mają jak ich rozróżnić, bo filtrują po typie.
  3. Domyślna kolejność aspektów — breaker liczy próby, nie operacje; próg 50% znaczy co innego, niż mówi.
  4. Kontrakt HTTP zwracał 409 na wszystko — także wtedy, gdy żądanie klienta było bez zarzutu, a to zależność leżała.

Do tego drobiazg z dużymi konsekwencjami: każda porażka inkrementowała dwa liczniki — raz domain/infrastructure w środku, raz circuit_open w fallbacku. Suma błędów była dwukrotnie zawyżona, a panel „trasy oddane do fallbacku" pokazywał wszystkie porażki, nie odcięcia.

Kolejne cztery rozdziały to cztery zmiany, które to naprawiają. Każda jest osobnym, samodzielnym krokiem — po każdym system się buduje i demo działa.

7. Zmiana 1 — fallback tylko na otwarty obwód

Resilience4j dopasowuje metodę fallbackową po typie parametru wyjątku. To nie jest szczegół implementacyjny — to mechanizm sterujący, którego można użyć celowo.

Przed
private Route routeUnavailableFallback(ReserveBayCommand command, Throwable t) {
    incrementErrorCounter("circuit_open");   // ← kłamstwo przy KAŻDYM błędzie
    throw new RouteUnavailableException(from, to, t);
}
Po
// Fallback dopasowuje się po typie parametru, więc odpala się WYŁĄCZNIE przy
// otwartym obwodzie. Każdy inny wyjątek przelatuje nietknięty — fallback typu
// Throwable połykał nasze własne bugi (NPE, OOM) i etykietował je jako circuit_open.
private Route circuitOpenFallback(ReserveBayCommand command, CallNotPermittedException e) {
    count("circuit_open");
    log.warn("Circuit open for trade-route-planner, failing fast: {} -> {}", from, to);
    throw new RoutePlannerUnavailableException(from, to, e);
}

Co to zmienia w praktyce: metryka outcome="circuit_open" rośnie teraz wyłącznie wtedy, gdy obwód jest faktycznie otwarty. Kafelek „Trasy oddane do fallbacku" na dashboardzie przestał kłamać — wcześniej rósł przy każdej awarii, zanim breaker w ogóle się otworzył. Zniknęło też podwójne liczenie: skoro fallback odpala się tylko przy odcięciu, żadna porażka nie jest liczona dwa razy.

Bonus bezpieczeństwa: NullPointerException z Objects.requireNonNull(command) nie przebiera się już za „trasa niedostępna" i nie wraca do klienta jako spokojne 409. Leci jako 500 — bo to jest błąd, nie degradacja.

8. Zmiana 2 — dwa typy wyjątków zamiast jednego

To jest centralna zmiana całej pracy. Nazwijmy antywzorzec po imieniu: kolaps semantyki błędu na granicy (exception type erasure). Trzy różne klasy awarii wchodzą do adaptera, wychodzi jeden typ — i wszystko poniżej traci zdolność ich rozróżnienia.

Nowa hierarchia

/** Planner ODPOWIEDZIAŁ i odmówił (4xx): deterministyczne odrzucenie domenowe.
 *  Drugie identyczne pytanie nie może dać innej odpowiedzi, więc retry tego nie
 *  ponawia, a breaker to ignoruje — fala odmów to nie awaria infrastruktury. */
public class RoutePlanningRejectedException extends RouteUnavailableException {
    private final int statusCode;   // niesie realny status HTTP plannera
}

/** Planner NIE ODPOWIEDZIAŁ użytecznie: 5xx, timeout, brak połączenia, puste
 *  ciało albo otwarty obwód. Jedyna rzecz, którą retry ponawia i którą breaker
 *  liczy jako porażkę. Mapowane na 503 + Retry-After. */
public class RoutePlannerUnavailableException extends RouteUnavailableException {
    private final int statusCode;   // 0, gdy odpowiedzi nie było wcale
}
Sztuczka, która czyni tę zmianę bezpieczną

Oba nowe typy dziedziczą po istniejącym RouteUnavailableException. Dzięki temu wszystkie istniejące bloki catch (RouteUnavailableException e) w ReservationService oraz stary handler mapujący na 409 działają dalej bez jednej linijki zmiany. To wzorzec wart zapamiętania przy refaktorze hierarchii wyjątków w żywym systemie: rozszerzaj w dół, nie w bok.

Adapter po zmianie

.onStatus(HttpStatusCode::is4xxClientError, (req, res) -> {
    // 4xx = odmowa domenowa ("tej trasy nie da się zaplanować") — deterministyczna,
    // więc nie wolno jej ani ponawiać, ani zapisywać w breakerze.
    count("domain");
    throw new RoutePlanningRejectedException(from, to, res.getStatusCode().value());
})
.onStatus(HttpStatusCode::is5xxServerError, (req, res) -> {
    // 5xx = awaria infrastruktury (planner leży) — przejściowa, do ponowienia.
    count("infrastructure");
    throw new RoutePlannerUnavailableException(from, to, res.getStatusCode().value());
})
// ...
catch (Exception e) {   // timeout / connection refused
    // OCZEKIWANA awaria zależności, nie bug w tym serwisie: jedna linia WARN,
    // bez stacktrace'u. Przy 4 req/s chaosu stacktrace na każdą próbę to
    // dokładnie ten szum w logach, przed którym ten system ma bronić.
    count("infrastructure");
    log.warn("Failed to plan route from {} to {}: {}", from, to, e.toString());
    throw new RoutePlannerUnavailableException(from, to, e);
}

I nagle konfiguracja czyta się jak zdanie po polsku

circuitbreaker.instances.trade-route-planner:
  ignore-exceptions:
    - ...routeplanner.RoutePlanningRejectedException     # odmowa to ODPOWIEDŹ, nie awaria

retry.instances.trade-route-planner:
  retry-exceptions:
    - ...routeplanner.RoutePlannerUnavailableException   # ponawiaj tylko to, co mogło się udać

Co to zmienia w praktyce. Wyobraź sobie falę klientów pytających o trasy, których fizycznie nie da się wytyczyć (za mały zasięg statku). Przed zmianą: same 4xx, każda ponawiana przez retry, każda zapisywana w oknie breakera jako porażka — failure rate przebija 50% i obwód odcina całkowicie zdrowego plannera. Po zmianie: te odmowy są dla breakera niewidzialne (ani sukces, ani porażka), retry ich nie dotyka, a klient dostaje szybkie 409 z sensownym komunikatem.

Trzecia kategoria, o której łatwo zapomnieć: nasze własne bugi

Rozdzielenie odmowy od niedostępności załatwia dwa przypadki. Jest jednak trzeci, który przez długi czas przechodził u nas niezauważony — i jest najbardziej podstępny, bo przekłamuje pomiar cudzego serwisu.

Wróćmy do pytania, na które ten bezpiecznik istnieje, żeby odpowiadać: „czy trade-route-planner jest zdrowy?". Skoro tak, to jedyną rzeczą, którą wolno mu zapisać jako porażkę, jest porażka tamtego serwisu. Tymczasem NullPointerException z naszego mapowania albo IllegalStateException ze złamanego inwariantu nie mówią o plannerze nic — bo do plannera w ogóle nie dotarliśmy.

Co robiła czarna lista — konkretny scenariusz

Mieliśmy samo ignore-exceptions: RoutePlanningRejectedException, czyli domyślną odpowiedzią było „licz jako awarię zależności". Wdrażasz zmianę, w której buildRequest rzuca NullPointerException na każdym wywołaniu:

  1. pięć wywołań → pięć „porażek" w oknie → failure rate 100% → obwód się otwiera;
  2. ruch dostaje 503 z Retry-After: 10 — czyli „zależność ma problem, wróć za chwilę". Ale ponowienie nic nie da: bug jest deterministyczny;
  3. odpala się alert TradeRoutePlannerCircuitOpen;
  4. dyżurny idzie sprawdzać trade-route-planner, który jest w idealnym stanie.

Zamieniliśmy własny bug w opowieść o cudzej awarii — i schowaliśmy go za czystą ścieżką degradacji. To jest dokładne przeciwieństwo tezy tego dokumentu: dashboard przestał mówić prawdę, tylko tym razem w drugą stronę.

Naprawa: biała lista zamiast czarnej

circuitbreaker.instances.trade-route-planner:
  # Bezpiecznik zapisuje jako porażkę WYŁĄCZNIE awarię tego serwisu.
  record-exceptions:
    - ...routeplanner.RoutePlannerUnavailableException
  ignore-exceptions:
    - ...routeplanner.RoutePlanningRejectedException     # odpowiedź domenowa, nie awaria
Ważny szczegół implementacyjny — trzy gałęzie, nie dwie

CircuitBreakerStateMachine#handleThrowable rozstrzyga w tej kolejności:

1. pasuje do ignore-exceptions → releasePermission() — wywołanie NIE trafia do okna 2. pasuje do record-exceptions → state.onError(...) — liczone jako PORAŻKA 3. żadne z powyższych → state.onSuccess(...) — liczone jako SUKCES

Nasze bugi lądują w gałęzi 3, czyli po zmianie są liczone jako sukces. To niedoskonałe — zawyżają licznik udanych wywołań i rozcieńczają slow-call rate — ale semantycznie obronne: na tyle, na ile ten bezpiecznik może stwierdzić, zależność nie zawiodła. Co ważniejsze, przestały otwierać obwód przeciw zdrowemu serwisowi i przestały odpalać cudzy alert.

Strukturalna naprawa jest inna i warto ją znać: zawęzić zasięg adnotacji tak, żeby obejmowała wyłącznie wywołanie zdalne. Dziś @CircuitBreaker siedzi na metodzie, która najpierw waliduje argumenty i buduje żądanie — więc bug z tych etapów w ogóle ma szansę dotrzeć do okna. Gdyby adnotacja obejmowała sam wyjazd na drut, gałąź 3 nigdy by się nie uruchomiła. To wymaga wydzielenia osobnego beana (samowywołanie omija proxy AOP) i jest w backlogu.

Reguła

Zakres adnotacji jest częścią kontraktu. Bezpiecznik mierzy dokładnie to, co obejmuje — jeśli obejmuje twój kod, będzie mierzył także twoje błędy i przypisywał je cudzemu serwisowi. Domyślną odpowiedzią na pytanie „czy to awaria zależności" powinno być nie, a nie tak.

Dlaczego filtrowanie po typie, a nie po polu

Można by zostawić jeden wyjątek z polem kind i rozróżniać w kodzie. Nie zadziała: ignore-exceptions i retry-exceptions w Resilience4j dopasowują po klasie. Ta sama zasada rządzi fallbackiem (zmiana 1) i — jak zobaczymy — rdzeniowym @Retryable w Springu 7. Typ wyjątku to nie szczegół implementacji; to zdanie, które twój kod mówi całej reszcie systemu.

9. Kolejność aspektów (cebula) — co mamy domyślnie i jak to odwrócić

To rzecz, na której wykładają się seniorzy, bo jest całkowicie niewidoczna w kodzie. Adnotacje na metodzie układają się w cebulę — jeden aspekt owija drugi. Domyślnie w Resilience4j:

DOMYŚLNIE: Retry ( CircuitBreaker ( metoda ) ) └─ zewnętrzny └─ wewnętrzny PO ZMIANIE: CircuitBreaker ( Retry ( metoda ) ) └─ zewnętrzny └─ wewnętrzny
Pułapka w pułapce

Pierwszy odruch to przełożyć adnotacje miejscami w kodzie. Nie zadziała — kolejność jest zaszyta w wartościach Ordered aspektów, nie w kolejności zapisu. Zmieniają ją wyłącznie właściwości konfiguracyjne.

Co my mamy — i dlaczego akurat to

W application.yml zostawiliśmy kolejność domyślną: Retry( CircuitBreaker( metoda ) ). Świadomie — bo to jest konfiguracja, którą ma każdy projekt, dopóki ktoś jej celowo nie zmieni, a liczenie próbami daje szybszą reakcję na twardą awarię. Odwrócenie leży w osobnym profilu cb-outer:

// application-cb-outer.yml — aktywacja: SPRING_PROFILES_ACTIVE=demo,cb-outer
resilience4j:
  circuitbreaker:
    circuit-breaker-aspect-order: 1   # niższa wartość = bardziej NA ZEWNĄTRZ
  retry:
    retry-aspect-order: 2

Profil istnieje po to, żeby różnicę dało się zobaczyć na wykresach, a nie tylko o niej przeczytać: te same żądania, ten sam wstrzyknięty chaos, jedna zmienna środowiskowa — i dwa różne obrazy zdrowia zależności na dashboardzie. To jest przekonujące w sposób, w jaki tabela nigdy nie będzie.

Dlaczego to ma znaczenie — arytmetyka

Gdy Retry jest na zewnątrz, breaker widzi każdą próbę osobno. Jedna operacja z max-attempts: 2 zostawia w oknie dwa wpisy. Weźmy przykład ilustracyjny z trzema próbami: dziesięć operacji, dwie padają. Człowiek liczy: 20% porażek, próg 50%, spokój. Breaker liczy próby: 2 porażki × 3 próby = 6 nieudanych wywołań, plus 8 udanych = 14 wpisów, z czego 6 czerwonych. 43% — o włos od otwarcia. Ta sama chwila, dwie zupełnie różne prawdy, zależnie od tego, kto liczy. To jest resilience4j issue #2383.

Dowód A/B — dwa testy różniące się dwoma liczbami

Żeby to nie pozostało teorią, w repozytorium leżą dwie klasy testowe. Różnią się wyłącznie dwoma intami — druga przywraca domyślną kolejność przez @TestPropertySource. Ten sam chwiejny planner (co drugi request zwraca 503, więc każdą operację ratuje retry), ta sama seria trzech operacji:

ObserwacjaRetry na zewnątrz (DOMYŚLNA — nasza baza)CB na zewnątrz (profil cb-outer)
Okno po jednej uratowanej operacji1 porażka + 1 sukces1 sukces / 0 porażek
Seria 3 operacji — wynik dla klienta2 × sukces, 3. rzuca wyjątkiem3 × sukces

Przeczytaj lewy słupek jeszcze raz, bo wynik domyślnej kolejności jest ostrzejszy, niż sugeruje sama teoria o „szybszym otwieraniu". Breaker otwiera się w połowie trzeciej operacji: piąty wpis w oknie daje 3 porażki na 5 wywołań, czyli 60% ≥ próg 50% przy minimum-number-of-calls: 5. W efekcie odrzuca retry tej samej operacji, którą retry właśnie ratował. Zależność odpowiedziała poprawnie na każdą operację — a klient dostał błąd.

To nie jest argument za tym, żeby natychmiast przestawiać produkcję. To argument za tym, żeby wiedzieć, w której kolumnie się jest — bo próg failure-rate-threshold: 50 znaczy w każdej z nich coś innego, a plik konfiguracyjny wygląda identycznie.

Uczciwa rama — to nie jest bug biblioteki

Obie kolejności są legalne i obie czemuś służą. Liczenie próbami (domyślne, nasza baza) daje wyższą czułość — breaker reaguje szybciej na twardą awarię, a retry z backoffem potrafi przeczekać krótkie otwarcie. Liczenie operacjami (profil cb-outer) daje przewidywalność progu: 50% znaczy 50% operacji i nie dryfuje przy zmianie max-attempts.

Nie do obrony jest tylko jedno: nie wiedzieć, którą z tych dwóch wersji ma się na produkcji. Dlatego obie są przybite testami — pomyłka w dwóch intach jest całkowicie bezobjawowa aż do pierwszej poważnej awarii.

Dwa testy, po jednym na każdą kolejność

Różnią się wyłącznie tym, że drugi startuje z aktywnym profilem. Reszta — zależność, ruch, asercje — jest napisana tak, żeby dało się je czytać obok siebie:

10. Zmiana 3 — backoff wykładniczy z jitterem

retry.instances.trade-route-planner:
  max-attempts: 2                    # UWAGA: 2 = pierwsza próba + JEDNO ponowienie
  wait-duration: 100ms
  enable-exponential-backoff: true
  exponential-backoff-multiplier: 2
  randomized-wait-factor: 0.5        # ±50% losowego rozrzutu

Przy dwóch próbach efekt praktyczny jest kosmetyczny: jedno czekanie 100 ms ± 50%. Ale kształt konfiguracji ma znaczenie dydaktyczne i operacyjne — ktoś skopiuje ten blok do serwisu z max-attempts: 5. Wtedy różnica jest ogromna:

  • Bez backoffu: pięć prób co 100 ms — dobijasz zależność, która właśnie próbuje wstać.
  • Bez jittera: wszystkie instancje twojego serwisu ponawiają w tej samej milisekundzie po odzyskaniu zależności. To klasyczny thundering herd — zależność wstaje, dostaje zsynchronizowaną falę i pada ponownie.

Jitter rozjeżdża te fale w czasie. To najtańsza linijka w całym pliku konfiguracyjnym w przeliczeniu na uniknięte incydenty.

11. Kontrakt HTTP: 409 kontra 503 + Retry-After

Ostatnia konsekwencja rozdzielenia wyjątków dotyczy tego, co widzi klient. Wcześniej każda utrata trasy kończyła się jako 409 Conflict.

// Awaria infrastruktury (planner 5xx/timeout/otwarty obwód): żądanie było W PORZĄDKU
// — komunikat brzmi "wróć za chwilę". 503 + Retry-After pozwala poprawnie napisanym
// klientom zaplanować ponowienie; 409 kazałoby im zmieniać żądanie, z którym nic nie
// jest nie tak. Retry-After = wait-duration-in-open-state (10 s), czyli najwcześniejszy
// moment, w którym obwód może się domknąć.
@ExceptionHandler(RoutePlannerUnavailableException.class)
ResponseEntity<Map<String, String>> handle(RoutePlannerUnavailableException ex) {
    return ResponseEntity.status(HttpStatus.SERVICE_UNAVAILABLE)
            .header(HttpHeaders.RETRY_AFTER, "10")
            .body(Map.of("error", "ROUTE_PLANNER_UNAVAILABLE", "details", ex.getMessage()));
}

// "nie" na TO żądanie — powtórzenie go bez zmian nie pomoże. 409.

Micrometer i Observation — jeden call, dwa sygnały

Micrometer jest dla metryk tym, czym SLF4J dla logów: jednym interfejsem, którego backend wybierasz zależnością w pom.xml. W Spring Boot 3 dochodzi Observation API — jedno owinięcie produkuje i metrykę, i span w trace'ie:

return Observation.createNotStarted(OBSERVATION_NAME, observationRegistry)
        .lowCardinalityKeyValue("startStarport", ...)
        .lowCardinalityKeyValue("destinationStarport", ...)
        .observe(() -> callTradeRoutePlanner(command));
Dlaczego „lowCardinality"

Każda unikalna kombinacja etykiet to osobna seria czasowa w Prometheusie. Kod portu (kilkadziesiąt wartości) jest bezpieczny. ID rezerwacji czy ID klienta — nie: wysadzi ci bazę metryk. Rzeczy o wysokiej kardynalności należą do trace'ów i logów, nie do etykiet metryk.

Jeden licznik napisany ręcznie — i dlaczego akurat ten

private final Map<String, Counter> outcomeCounters = new ConcurrentHashMap<>();

private void count(String outcome) {   // success | domain | infrastructure | empty_response | circuit_open
    outcomeCounters.computeIfAbsent(outcome, value -> Counter.builder("reservations.route.plan.outcome")
                    .description("Route planning attempts by outcome")
                    .tag("outcome", value)
                    .register(meterRegistry))
            .increment();
}

Metryki Resilience4j mówią językiem infrastruktury: „obwód otwarty", „60% wywołań failed". Ten jeden licznik mówi językiem produktu: ile REZERWACJI straciło trasę i dlaczego. To jedyne przełożenie techniki na rozmowę z biznesem — i jedyny licznik w tym module, który trzeba było napisać samemu.

Dwie decyzje w tych sześciu linijkach, obie zapłacone doświadczeniem

Jeden meter z tagiem, nie para success/errors. Pierwotnie były dwa osobne liczniki — i nie dało się policzyć success-ratio jednym wyrażeniem PromQL, bo trzeba było łączyć dwie różne nazwy metryk. Jeden meter z tagiem outcome daje sum by (outcome) (rate(...)) / sum(rate(...)) od ręki.

Nazwa NIE brzmi reservations.route.plan — mimo że tak byłoby najładniej. Ta nazwa należy już do Timera generowanego przez Observation kilka akapitów wyżej, a Micrometer odrzuca dwa różne typy metryki pod jedną nazwą. Aplikacja po prostu by nie wstała. Stąd sufiks .outcome.

Counter cache'owany w mapie, nie budowany przy każdym wywołaniu: Counter.builder(...).register(...) w gorącej ścieżce alokuje Meter.Id i robi lookup za każdym razem. Micrometer to deduplikuje, więc jest poprawnie — tylko niepotrzebnie.

Pomiar, który obalił hipotezę — warto o tym pamiętać

Zakładaliśmy, że wstrzyknięcie timeoutu na 50% wywołań da ~50% failure rate i otworzy obwód. Pomiar pokazał failure ~0%, slow ~10%, obwód zamknięty. Przyczyna: toksyna Toxiproxy działa per połączenie, a pula keep-alive obsługuje większość żądań po już nawiązanych, zdrowych połączeniach. Nominalna „toksyczność" nie równa się procentowi dotkniętych żądań.

Morał wykracza poza to narzędzie: nie ufaj nominalnym parametrom narzędzia do chaosu — mierz rezultat. Gdybyśmy oparli demo na założeniu zamiast na pomiarze, na scenie nie zadziałałoby to, co obiecaliśmy.

14. Spring Framework 7 / Boot 4 — co się zmienia, a co zostaje

W listopadzie Spring Framework 7.0 wnosi rdzeniowe wsparcie dla odporności: adnotacje @Retryable i @ConcurrencyLimit, włączane przez @EnableResilientMethods, plus programistyczny RetryTemplate. Zero zewnętrznych zależności. To dobra wiadomość — i nie zwalnia z niczego, o czym mówi ten wykład.

Co dokładnie dostajesz

@Retryable(
  includes = MessageDeliveryException.class,
  maxAttempts = 5, delay = 100, jitter = 10, multiplier = 2, maxDelay = 1000)
public void sendNotification() { ... }

@ConcurrencyLimit(10)                      // ogranicza równoległość do 10
public void sendNotification() { ... }
  • @Retryable — domyślnie 3 ponowienia po pierwszej porażce, 1 s odstępu, dla każdego wyjątku. Zawężasz przez includes, excludes, predicate. Ma wbudowany jitter, multiplier, maxDelay. Działa też dla metod reaktywnych — dekoruje pipeline mechanizmem retry z Reactora.
  • @ConcurrencyLimit — oparty na ConcurrencyThrottleInterceptor (obecnym w Springu od wersji 1.0). Wartość 1 działa jak zamek na instancję beana.
  • RetryTemplate + RetryPolicy.builder() — wariant programistyczny dla dowolnych bloków kodu.
  • Projekty portfolio (Boot, Batch, Integration, AMQP, Kafka, Pulsar) już migrują ze Spring Retry na rdzeń.
Ciekawe potwierdzenie z pierwszej ręki

Dokumentacja Springa uzasadnia @ConcurrencyLimit tym, że ograniczanie równoległości jest szczególnie przydatne przy wirtualnych wątkach, gdzie nie ma już limitu puli. To ta sama obserwacja, która w naszym projekcie (wirtualne wątki od ADR-0012) unieważnia klasyczny argument „wolna zależność zje ci pulę wątków". Pod wirtualnymi wątkami pula nie jest wąskim gardłem — są nim połączenia HTTP i pamięć. Jeśli używasz wirtualnych wątków, musisz ograniczać równoległość świadomie, bo runtime przestał robić to za ciebie.

Czego w rdzeniu NIE ma

Najważniejsze zdanie tego rozdziału: w rdzeniu Springa nie ma circuit breakera. Nie ma też slow-call detection, deklaratywnego fallbacku ani gotowych metryk stanu obwodu. Po to wciąż idziesz do Resilience4j.

A skoro po breakera idziesz do Resilience4j, a po retry możesz sięgnąć do rdzenia Springa — składasz dwa aspekty z dwóch różnych frameworków na jednej metodzie. Pytanie „co widzi breaker: operację czy próbę?" wraca w wersji trudniejszej, bo kolejność trzeba teraz uzgodnić między bibliotekami, a nie w obrębie jednej.

Wniosek

Zmienia się dostawca adnotacji. Cebula zostaje. Wiedza z rozdziału 9 nie traci ważności — zyskuje na niej.

15. Pułapki migracji na rdzeniowe @Retryable

Jeśli kiedyś będziesz przenosić naszą konfigurację na Spring Framework 7, są cztery miejsca, w których dosłowne przepisanie wartości da inne zachowanie.

Pułapka 1: maxAttempts znaczy co innego w każdym z trzech światów

ŚwiatmaxAttempts = 2 to…Łącznie wywołań
Resilience4j (nasz kod)pierwsza próba + 1 ponowienie2
Spring Retry (stary projekt)pierwsza próba + 1 ponowienie2
Spring Framework 7 (rdzeń)2 ponowienia — pierwsze wywołanie się nie liczy3

Czyli dosłowne przepisanie max-attempts: 2 z naszego application.yml do @Retryable(maxAttempts = 2) zwiększa ruch do zależności o 50%. Domyślna wartość w rdzeniu (3 ponowienia) oznacza cztery wywołania na operację. Przy okazji: to podwaja znaczenie kolejności aspektów, bo im więcej prób, tym mocniej rozjeżdżają się „procent operacji" i „procent prób".

Pułapka 2: jitter to inny model liczbowy

Resilience4j: randomized-wait-factor: 0.5 — rozrzut względny, ±50% aktualnego odstępu. Spring 7: jitter = 10 — wartość bezwzględna w milisekundach. Przepisanie 0.5 jako jitter da 0,5 ms rozrzutu, czyli praktycznie brak jittera przy zachowanej nazwie parametru. Klasyczna cicha regresja.

Pułapka 3: @ConcurrencyLimit blokuje, nie odrzuca

To nie jest zamiennik semaforowego Bulkhead z Resilience4j ustawionego na max-wait-duration: 0. Przy pełnym limicie wątki czekają, zamiast dostać natychmiastową odmowę. Konsekwencja operacyjna: pod przeciążeniem rośnie ci latencja i długość kolejki zamiast liczby szybkich odmów. Jeśli świadomie chcesz fail-fast — a często chcesz, bo szybka odmowa jest uczciwsza niż czekanie w kolejce, której klient i tak nie doczeka — zostajesz przy Resilience4j.

Pułapka 4: nie mieszaj obu retry na jednej metodzie

Kolejność aspektów między frameworkami nie jest gwarantowana kontraktem — zależy od wartości Ordered i kolejności rejestracji post-procesorów po obu stronach. Trzymaj jednego dostawcę retry na metodę, a jeśli musisz łączyć — rozdziel na osobne beany i udowodnij zachowanie testem, dokładnie tak jak w rozdziale 9.

16. Checklista do własnego projektu

Krótka lista rzeczy, które warto sprawdzić w dowolnym serwisie wołającym inny serwis — kolejność odzwierciedla stosunek zysku do wysiłku.

  1. Czy masz connect- i read-timeout? Jeśli nie, wszystko poniżej jest bez znaczenia — nadal możesz wisieć w nieskończoność.
  2. Czy breaker liczy CZASY, nie tylko błędy? Bez slow-call detection awaria typu „niby działa" jest dla ciebie niewidzialna.
  3. Czy próg slow-call jest poniżej read-timeoutu? Jeśli powyżej — nigdy się nie uruchomi.
  4. Czy retry ponawia wyłącznie porażki przejściowe? Sprawdź konkretnie, czy 4xx nie wpadło przypadkiem do retry-exceptions przez wspólny typ nadrzędny.
  5. Czy breaker ignoruje odrzucenia domenowe? Inaczej fala poprawnych „nie" odetnie ci zdrową zależność.
  6. Którą kolejność aspektów masz? Sprawdź w konfiguracji, nie w kodzie — i przybij testem.
  7. Czy fallback łapie konkretny typ, a nie Throwable? Inaczej twoje bugi przebierają się za degradację.
  8. Czy status HTTP mówi klientowi prawdę? 503 + Retry-After dla awarii, 4xx dla błędu żądania.
  9. Czy widać, że mechanizmy zadziałały? Retry, który po cichu ratuje 30% wywołań, ukrywa chorą zależność.
  10. Czy masz alert na otwarty obwód? I czy wiesz, po jakim czasie realnie przejdzie w FIRING?

Czego świadomie nie zrobiliśmy (backlog)

  • Jeden licznik reservations.route.plan z tagiem outcome zamiast pary sukces/błędy — wymaga przepisania zapytań dashboardu.
  • sliding-window-type: TIME_BASED (60 s) zamiast licznikowego okna 10.
  • Klucz idempotencji dla ponawianego POST-a — bez niego timeout po przetworzeniu żądania może zduplikować zdarzenie trasy.
  • Optional<Route> zamiast zwracania null, gdy trasa nie jest wymagana.
  • Przeniesienie reguły „klasa statku → zasięg" z adaptera HTTP do domeny.
Jedno zdanie na koniec

System będzie się psuł — sieć padnie, zależność zwolni, ktoś wdroży zły adres. Nie chodzi o to, żeby się nie psuło. Chodzi o to, żeby psucie było widać — i żeby każdy mechanizm obronny umiał powiedzieć, kiedy i dlaczego zadziałał.
